Web Form Reference

This page is a live reference for the RD3 Tech Web Form and its relationship with FIELD_SCHEMA, the WordPress contact form, Web App POST parameters and the submission pipeline.

FIELD_SCHEMA is supplied by the configuration system. This page does not create or maintain a second schema.

1. Web Form Configuration Overview

The RD3 Tech Web Form uses FIELD_SCHEMA as the reference for field identity and mapping.

The WordPress contact form provides the visitor-facing interface. It sends the submitted values to the RD3 Tech Web App.

Important: The WordPress form does not create a second FIELD_SCHEMA. FIELD_SCHEMA remains the source of truth for the RD3 Tech field definitions and their relationships.

6. Adding or Changing a Web Form Field

When adding a field

  1. Add or update the field in FIELD_SCHEMA.
  2. Confirm the schema key.
  3. Confirm the WordPress HTML field ID.
  4. Confirm the JavaScript POST parameter.
  5. Confirm the field type.
  6. Confirm required/optional status.
  7. Confirm the field is mapped correctly.
  8. Test the WordPress Web Form.
  9. Test the submission pipeline.
  10. Test the email templates.
Do not create a second FIELD_SCHEMA inside the Web Form. The WordPress form is the user interface. FIELD_SCHEMA remains the configuration source of truth.

7. Web Form Diagnostic

Browser-side checks performed against the live FIELD_SCHEMA.

The following checks are performed in the browser.

  • FIELD_SCHEMA exists.
  • FIELD_SCHEMA contains fields.
  • Each field has a schema key where expected.
  • Each field has a form field where expected.
  • Each field has an entry ID where expected.
  • No unresolved Apps Script scriptlets remain after rendering.

8. WordPress Web Form Integration

WordPress Fluent Snippets implementation and field mapping reference.

Important: The WordPress contact form is the visitor-facing interface. It sends form-urlencoded POST parameters to the RD3 Tech Web App. It does not own FIELD_SCHEMA.

WordPress Fluent Snippet

The current implementation is intended to be installed as a PHP Fluent Snippet using the shortcode: 

[rd3_contact_form_refresh]

The configuration is controlled by: 

function rd3_contact_form_config() {

    return [
        'endpoint' => 'https://script.google.com/macros/s/YOUR_WEB_APP_ID/exec',

        'client_types' => [
            'Home or Family',
            'Small Business',
            'Community Group'
        ],

        'help_categories' => [
            'Help with Something Broken?',
            'Help with Something Better?',
            'Help with Your Workplace Technology?',
            'Help with Managing Your IT?',
            'Help with Technology Consulting or Advice?',
            'Help with Knowing Where to Start?',
        ],

        'urgency_options' => [
            'Low',
            'Medium',
            'High'
        ],

        'contact_preferences' => [
            'Email',
            'Phone'
        ],

        'previous_client_options' => [
            'Yes',
            'No'
        ],

        'previous_client_options' => [
            'Yes',
            'No'
        ],
    ];
}
Production endpoint: Keep the real production endpoint in the WordPress Fluent Snippet. This documentation uses YOUR_WEB_APP_ID so the reference page does not become another copy of the production endpoint.

Where To Change The WordPress Form

Dropdown configuration is changed inside: 

rd3_contact_form_config()

For example, to add another client type: 

'client_types' => [
    'Home or Family',
    'Small Business',
    'Community Group',
    'Not-for-Profit'
],

To change urgency options: 

'urgency_options' => [
    'Low',
    'Medium',
    'High',
    'Critical'
],

To change contact preferences: 

'contact_preferences' => [
    'Email',
    'Phone',
    'Either'
],
Configuration boundary: Changing these WordPress arrays changes the choices presented to the visitor. It does not automatically change FIELD_SCHEMA.

How To Change A Field

When changing a Web Form field, keep the following chain aligned: 

1. WordPress HTML
       |
       +-- id
       |
       v

2. JavaScript payload
       |
       +-- POST parameter
       |
       v

3. FIELD_SCHEMA
       |
       +-- key
       +-- formField
       +-- entryId
       +-- type
       |
       v

4. RD3 Tech pipeline
       |
       v

5. Email templates
Do not change only the HTML ID. The HTML ID is used by JavaScript to locate the value. The JavaScript payload parameter is what is actually sent to the Web App. The corresponding server-side mapping and FIELD_SCHEMA must remain aligned.

What To Change Where

Change Location FIELD_SCHEMA?
Change visible field label WordPress HTML Usually no
Change dropdown options rd3_contact_form_config() Usually no
Change Web App endpoint endpoint No
Change POST parameter JavaScript payload.append() Yes — mapping must remain aligned
Change schema key FIELD_SCHEMA Yes
Change Google Forms entry ID FIELD_SCHEMA Yes
Change email template field Email template / pipeline mapping Check FIELD_SCHEMA first
Source-of-truth rule: The WordPress form is the user interface. The Web App is the transport and processing layer. FIELD_SCHEMA is the RD3 Tech field configuration source of truth. Do not create another FIELD_SCHEMA inside WordPress or inside this reference page.

9. Web Form Maintenance Checklist

  1. Confirm the field exists in FIELD_SCHEMA.
  2. Confirm the FIELD_SCHEMA key.
  3. Confirm the WordPress HTML ID.
  4. Confirm the JavaScript POST parameter.
  5. Confirm the Web App receives the parameter.
  6. Confirm the pipeline maps the field correctly.
  7. Confirm AdminEmail.html.
  8. Confirm ClientEmail.html.
  9. Submit a real test enquiry.
  10. Verify the complete email and client-data flow.
Never fix a mapping problem by adding a second schema. Fix the field relationship at the correct layer.
